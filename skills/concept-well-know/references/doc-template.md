# 文档模板与写作规则

## 一、文档骨架

按顺序组织，方括号节可按主题裁剪：

```markdown
# <主题>：概念与公式梳理

> 一句话定位：<主题>是什么、解决什么问题。（加粗核心短语）

## 1. 在整体中的作用
## 2. 发展史与演变脉络    [如有明确演变史]
## 3. 符号表
## 4. 各方法/概念展开      （主体，占全文 60% 以上）
## 5. 横向对比            [两个以上方法时必有]
## 6. 总结：选型建议与常见误区
## 7. 参考资料
```

**章节衔接（硬要求）**：按主题的真实关系组织：前置概念按依赖顺序讲，
并列方法按分类或对比展开，等价形式说明各自的视角。只有一手来源支持改进关系时，
才使用“问题 → 解决 → 新问题”的链，不把所有方法都写成上一方法的修补。具体规则：

- 每个一级节开头用一两句说明与前文的关系：依赖、分类、对比或有来源支持的改进。
- 读者应能理解本节的位置与作用；并列方法和等价形式不必回应上一节的遗留缺陷。
- 衔接句提供实际关系，不写“接下来介绍”之类的目录句，也不补造因果或历史继承关系。

### 1. 在整体中的作用

回答"它在更大的系统里扮演什么角色"：

- 放进上下文：它处在哪条 pipeline 的哪个环节（如：优化器 = 训练循环里"拿梯度更新参数"的那一步）。
- 它解决的核心矛盾是什么；没有它/它做差了会发生什么。
- 一张位置示意图（Mermaid 流程图即可），标出主题所在环节。

### 2. 发展史与演变脉络

只有主题存在可查证的演变史时才写；可按时间线或并行分支组织，不强求单线因果链。

- 用时间线表达：`年份 — 方法 — 研究目标或有来源支持的改进动机`。
- 有来源支持时说明改进针对的缺陷；独立提出的路线保留为并行分支，不推断继承关系。
- 可用 Mermaid timeline / graph 画演变树（有分支时尤其值得画）。

### 3. 符号表

全文统一的符号表，先于任何公式出现：

| 符号 | 含义 | 形状/取值 |
|---|---|---|
| $\theta_t$ | 第 $t$ 步参数 | $\mathbb{R}^d$ |
| $g_t$ | 第 $t$ 步梯度 $\nabla_\theta \mathcal{L}(\theta_t)$ | $\mathbb{R}^d$ |

规则：同一符号全文不重载；向量/矩阵/标量的记法区分清楚；上下标含义固定。

### 4. 各方法/概念展开（主体）

每个方法/概念用固定小骨架，缺哪项写哪项的理由（如"性质无闭式结论，略"）：

```markdown
### 4.x <方法名>（<提出年份，出处>）

**动机/直觉**：一两句说明该方法解决什么问题、依赖哪些概念或提供什么不同视角；
有来源支持的改进关系时，再说明它回应了此前方法的什么缺陷。

**定义与公式**：

$$
\theta_{t+1} = \theta_t - \eta \, g_t \tag{4.x.1}
$$

**推导**（关键步骤，每步标依据）：
从 <出发点> 出发 → <关键变换，依据> → 得 (4.x.1)。

> 💡 例：数值代入或具体场景，两三行把上面的机制走一遍。

**性质**：收敛性/不变性/复杂度等，可列表。

**优缺点**：
- ✅ 优点（各一句话，说清"为什么"）
- ❌ 缺点

**主要用途与实际作用**：在什么场景默认用它、实践中的典型表现/超参习惯。
```

推导要求：

- **连贯**：一条推导线从头走到尾，不许各小节各写各的、符号对不上。
- 跳步必须标注：`> 📌 补充推导：`；直接引用原文结论标 `（原文 Eq.N）`。
- 推导中的每个约等号/不等号写明依据（Taylor 展开到几阶、Jensen、Cauchy-Schwarz……）。

例子要求（帮助理解的硬手段，不是装饰）：

- 每个方法至少一个落地例子。首选**数值代入**——拿具体的数把公式走一遍，如
  "$\beta_1{=}0.9$，前两步梯度 $g_1{=}1, g_2{=}0$，则 $m_2 = 0.09$——梯度已归零，动量仍推着走"；
  次选贴工程/科研背景的类比；生活化类比基本不用，凑数不如不写。
- 例子要演示**机制**（代入后能看出"为什么会这样"），不是把结论换个说法重复一遍。
- 克制：两三行、每方法一个就够；机制本身足够直白时可省。

### 5. 横向对比

两个以上方法时必有对比表。选维度的原则：**读者选型时真正会问的问题**。

| 方法 | 核心更新式 | 额外状态/开销 | 超参敏感度 | 典型场景 |
|---|---|---|---|---|

- 表格单元格只放短结论，解释放表格前后的正文。
- 有"演变关系"的方法组，可在表后补一张 Mermaid 关系图。

### 6. 总结

- 3–5 条要点回顾（每条加粗核心短语）。
- 选型建议：什么情况用什么，一两句话一条。
- ⚠️ 常见误区：把容易搞混/搞错的点列出来（这是全文复习价值最高的部分之一）。

### 7. 参考资料

一手来源列表：论文（标题 + 年份 + arXiv/DOI 链接）、教科书（书名 + 章节）。
正文引用过的必须都在；没引用过的不放。

## 二、公式与正确性写法

- 行内 `$...$`，独立公式 `$$...$$`；被引用的公式必须编号。
- 编号写法看目标渲染器（工作流第 1 步确认）：Typora / Obsidian 用 `\tag{4.x.1}`；
  GitHub 不渲染 `\tag`，退化为在公式行尾写 `\qquad (4.x.1)`。
- 公式先于文字结论：先给式子，再解释每一项的含义（"其中 $\beta_1$ 控制……"）。
- 关键公式的**每个非平凡项都要有一句话解释**，不许甩公式不解释。
- 等价形式值得写：同一概念的不同视角（如卷积的求和式/矩阵式/频域式）分别给出并说明何时好用。

## 三、重点标注与颜色约定

基础标注（所有渲染器可用，优先用这套）：

- **加粗**：关键结论、核心短语、术语的正式定义处。
- *斜体*：轻度强调、英文术语/论文名/书名、非正式定义的引入性提及（正式定义仍用加粗）。
- `> 💡` 直觉/类比；`> 💡 例：` 落地例子（数值代入/场景，见第一节例子要求）；
  `> ⚠️` 易错点、坑；`> 📌 补充：` 超出一手来源的自行补充。
- 强调要克制：一段内加粗/斜体超过两三处等于没有强调。

颜色（可选增强，用 HTML span，最多三色，全文含义固定）：

- <span style="color:#c0392b">红 `#c0392b`</span>：易错点、关键警告
- <span style="color:#2b6cb0">蓝 `#2b6cb0`</span>：首次出现的核心术语/定义
- <span style="color:#2f855a">绿 `#2f855a`</span>：实践建议、经验值

写法：`<span style="color:#c0392b">**易错**：卷积在深度学习框架里实际是互相关</span>`。

> ⚠️ 兼容性：HTML 颜色在 Typora / Obsidian / VS Code 预览有效，GitHub 会剥离 style。
> 目标渲染器在工作流第 1 步确认；GitHub 场景退回"基础标注"，或在公式内用 `$\color{red} ...$`。

## 四、配图与题注规则

- **图注**放图片下方：`**图 N**：一句话说明。图源：<论文名>, Fig.M`
  （自绘图统一写"示意图，自绘"；codex 绘制的写"示意图，自绘（codex 生图/脚本）"）。
- **表注（题注）**放表格上方：`**表 N**：一句话说明`。全文所有表格（含符号表、对比表）都要有题注。
- 图、表分别独立连续编号；正文引用写"见图 N / 表 N"，不写"上图/下表"。
- 用相对路径引用 assets 目录：`![Adam 更新示意](<短名>_概念梳理.assets/adam_update_rule.png)`。
- 优先原论文图（曲线对比、架构图）；自绘 Mermaid 图标注"示意图"。
- 图不是装饰：每张图要回答一个问题（演变关系？几种方法轨迹差异？模块数据流？），
  回答不了任何问题的图删掉。

## 五、语言风格

- 简洁精炼：一句话能说清的不写两句；删掉"值得注意的是""综上所述"这类填充语。
- 每段只说一件事；长解释拆列表。
- 不堆砌形容词，判断句要有依据（公式、引用或标注为经验）。
- 中文行文，术语/符号/方法名保留英文；首次出现的英文术语给一次中文对照，
  抽象术语再补一句大白话括号解释（如"病态曲率（loss 面在某些方向陡、某些方向平，
  一个学习率照顾不过来）"）——只解释这一次，后文直接用术语。
- 抽象判断句落到具体：写"对稀疏梯度友好"这类结论时，跟半句具体所指
  （"embedding 层大多数行长期没有梯度"），不让读者自己脑补场景。
- 全文写完后通读一遍去 AI 味：删排比、删空洞总结句、合并重复表述。
