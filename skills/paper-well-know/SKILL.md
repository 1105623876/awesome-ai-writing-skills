# paper-well-know：单篇论文精读报告

把一篇论文读透，写成一份**依据原文**、图文并茂、简洁不啰嗦的中文梳理报告 `.md`。

## 输出约定

- 报告用简体中文；术语、符号、数据集、方法名、指标名保留英文原词。
- 报告名 `<论文短名>_精读.md`，写进 `notes/`；图片写进 `asserts/`。两个目录怎么定位见下面「输出位置」。
- **默认允许并优先使用论文原始图片**（从论文 PDF 提取/截取，或从官方 HTML / ar5iv 下载原图），无需用户在指令中额外声明"允许截图"；Mermaid 重绘只作提取失败时的兜底（见"默认工作流"第 4 步）。
- 图片文件名用可读的 ASCII 小写短名，**并带论文短名前缀**：`<论文短名>_fig2_architecture.png`、`<论文短名>_table1_main_results.png`。

## 输出位置（严格遵守，不要随意建目录）

用户一般给论文的**绝对路径**。从论文文件所在目录出发**向上最多找两层**，定位这些**已存在**的目录，找到就用：

| 产物 | 目录 | 文件名 |
|---|---|---|
| 精读报告 | `notes/` | `<论文短名>_精读.md` |
| 图片（提取图、裁剪图、下载的原图） | `asserts/` | `<论文短名>_fig2_architecture.png` |

典型布局——PDF 在 `raw_papers/`，其余是它的兄弟目录：

```
News/08/
├── raw_papers/   ← 论文 PDF
├── notes/        ← 精读报告
├── translate/    ← 翻译文档（paper-translate 的产物，本 skill 不写）
└── asserts/      ← 图片，扁平存放
```

规则：

- 目录名就是 `asserts`（用户的既有拼法），**不要"纠正"成 `assets`**。
- **图片扁平放在 `asserts/` 根下**，不建 `<论文短名>_精读.assets/` 之类的子目录。
- **图片名必须带论文短名前缀**——多篇论文共用一个 `asserts/`，不加前缀会被别篇同名的 `fig1_overview.png` 静默覆盖。
- **向上两层内找不到目标目录时停下来问用户**：把找过的路径列出来，让用户指定位置或确认在哪里建。不要自己建，也不要退回"写在论文同目录"。
- 用户在指令里明确指定了输出路径时，一律以用户指定的为准。
- 输入是 URL / arXiv 链接、没有本地论文文件时，以当前工作目录为起点按同样规则向上找；找不到就问。
- **唯一允许自建的目录**是本次的中间产物目录 `asserts/_tmp_<论文短名>/`（整页渲染图、转出的中间文本等都放这里），收尾时整个删掉。
- `<论文短名>` 取法：论文标题里最具辨识度的 1-3 个词转小写下划线连写（`Attention Is All You Need` → `attention_is_all_you_need`）；已有本地 PDF 时直接用其文件名主干。

## 边界

- 只处理**单篇**论文精读。多篇综述或定期论文推送应改用当前环境中相应的文献综述/自动化工作流；没有对应工具时先向用户说明边界。
- 不写 rebuttal、不做审稿意见回复。
- 报告内容以原文为准；你自己的补充解释必须显式标注（见"忠实性规则"）。
- 不凭模型记忆写论文细节。当前环境无法读取 URL 时，要求用户提供 PDF/HTML 或说明无法继续。

## 输入判定

| 输入 | 处理 |
|---|---|
| 本地 PDF 路径 | 直接读取或用 `pdftotext` 分批读取（见“可用工具与环境检查”）；长论文按页分块，但必须覆盖全文 |
| 本地 HTML | 直接读取 HTML 正文，保留图片 URL、公式编号、表格编号 |
| arXiv 链接 / ID | **优先取 HTML 版**：`https://arxiv.org/html/{id}`；不存在则试 `https://ar5iv.org/abs/{id}`；记录 arXiv 版本号 |
| 其他 URL | 用当前代理可用的网页读取工具获取正文；图片按 HTML 路线处理 |

## 可用工具与环境检查

先用 `command -v <工具名>` 检查工具是否在 `PATH` 中；命令示例均直接使用工具名。若用户已有包含这些工具的 Conda 环境，也可用 `conda run -n <环境名> <工具名> ...`。缺少工具时先说明受影响的功能，未经用户同意不要自行安装依赖，也不要假定某个用户目录或环境名存在。

| 工具 | 用途 | 典型命令 |
|---|---|---|
| `pdftotext` | PDF 提取纯文本（长论文分页读） | `pdftotext -f 1 -l 8 -layout paper.pdf -` |
| `pdftoppm` | PDF 整页渲染成图片 | `pdftoppm -png -r 150 -f 3 -l 3 paper.pdf page` |
| `pdfimages` | 提取 PDF 内嵌图片 | `pdfimages -png -f 2 -l 4 paper.pdf fig` |
| `pdfinfo` | 查页数、元信息 | `pdfinfo paper.pdf` |
| `markitdown` | pdf/docx/pptx/xlsx/html 等转 Markdown | `markitdown paper.pdf -o paper.md` |
| `pandoc` | docx/html/LaTeX/epub 等格式互转 | `pandoc paper.docx -t markdown -o paper.md` |

不要假定 `ffmpeg` 或 `markitdown` 的可选依赖已安装；本 skill 的论文阅读流程不依赖音频转录。

## 读论文前的证据记录

先建立一份工作笔记（不必交付），至少记录：

| 项 | 必填内容 |
|---|---|
| 论文身份 | 标题、作者、机构、会议/期刊或 arXiv 版本、链接 |
| 核心贡献 | 原文贡献声明所在段落或小节 |
| 方法证据 | 关键 Figure、Algorithm、Equation 编号及其作用 |
| 实验证据 | 主结果表、消融表、关键图、指标定义 |
| 不足证据 | limitation、failure case、future work 或原文未说明项 |

写报告时每个重要判断都要能回到这份证据记录。证据不足时写"原文未说明"，不要补成事实。

## 默认工作流

1. **锁定来源版本**。确认论文标题、版本、链接和用户提供的源是否一致。PDF、HTML、arXiv 版本不一致时，以用户给的源为准，并在报告头注明。
2. **通读全文**。先完整读完（PDF 分批读），记录贡献声明、方法核心公式、实验表格编号、关键图编号。不许只读 abstract + intro 就动笔。
3. **确定输出位置**。按「输出位置」向上找 `notes/` 和 `asserts/`，找不到就问，别自己建；不要把最终产物放在临时目录。
4. **提取图片**（按顺序降级）：
   1. 论文有 HTML 版 → `curl -o` 直接下载 `<img>` 指向的图片文件；
   2. 用 `pdfimages` 提取内嵌图，或用 `pdftoppm` 整页渲染后裁剪（路径与命令见“可用工具与环境检查”）；
   3. 以上都失败 → 用 Mermaid 重绘架构图 + 文字描述兜底，并在报告中注明"示意重绘，非原图"。
 5. **写报告**。先读 `references/report-template.md`，严格按五段结构和各节写作要求执行。
    - **方法部分必须画出完整流程图**：用 Mermaid 或文字描述，标注每个模块的输入/输出/处理过程，让读者一眼看清数据如何从输入流向最终输出。
    - **核心思想和方法细节要多写**：不要只写结论，要写清楚"为什么这样设计"、"每个模块解决什么问题"、"模块间如何协作"。
 6. **自检**，全部通过才算完成：
- [ ] 报告头包含论文来源版本，避免 PDF/HTML 版本混用；
     - [ ] **"本文的核心思想"章节末尾有一句话加粗总结**，一句话能说清"这篇论文到底做了什么、为什么重要"；
     - [ ] **方法部分有完整流程图**，标注了每个模块的输入/输出/处理过程；
    - [ ] 每个数学符号在首次使用前已在符号表或正文中定义；
    - [ ] **数学推导连贯**：符号表统一、推导按逻辑顺序展开，不能分散在各模块各写各的；
    - [ ] 推导每一步有依据（原文公式编号，或标注为补充推导）；
    - [ ] 所有实验数字能在原文表格/图中找到出处；
    - [ ] 你补充的内容全部带 `> 📌 补充：` 标记；
    - [ ] 报告内图片相对路径有效（`notes/` 里引用 `asserts/` 要写 `../asserts/<论文短名>_xxx.png`），且没有落下未使用的关键图；
    - [ ] 写进 `asserts/` 的图片全部带论文短名前缀，没有覆盖别篇论文的同名图；
    - [ ] 没有把二手博客、代码 README 或模型记忆写成论文原文事实；
    - [ ] 语言过一遍去 AI 味检查（见模板末尾的风格规则）。
7. **交付说明**。最终回复只需给出报告路径、图片目录、已验证项和未解决限制；不要把整篇报告复制到聊天里。
8. **收尾清理（仅在用户明确说任务完成后执行，不许提前）**。前提是每一步产生中间文件时
   就写进 `asserts/_tmp_<论文短名>/`（整页渲染图、未被引用的提取图、转出的中间文本、
   落盘的工作笔记），别指望事后再从别处捡。
   交付后中间产物先保留供用户对照；等用户明确表示任务完成/满意时，**只删
   `asserts/_tmp_<论文短名>/` 这一个整目录**，路径写全、不带通配符。
   - **`asserts/` 是多篇论文共用的目录，绝不许在它根下做"删除未被本报告引用的图"这类清理**——
     那些图属于别篇论文。
   - **绝对不删**：用户提供的论文源文件（PDF/HTML）、成品 `.md`、被报告引用的图片、
     `asserts/` 根下任何本次之外的文件。
   - 删除前先列出待删清单再执行，删除后报告删了哪些；拿不准的一律保留。
   - `_tmp_<论文短名>/` 之外若发现疑似残留，**只报告、不自己删**。

## 忠实性规则

- **原文优先**：论断、数字、结论必须出自论文本身，标注来源（如 "（§3.2, Eq.5）"、"（Table 2）"）。
- **补充要标注**：允许补充背景知识、补全跳步推导、给直觉解释，但一律用引用块 `> 📌 补充：` 开头，让读者一眼分清哪些是论文说的、哪些是你补的。
- **不确定就说不确定**：原文没写清楚的（如超参细节），写"原文未说明"，不要脑补成事实。
- **二手资料降权**：博客、GitHub README、项目页、新闻稿只能帮助理解，不能替代论文证据；若引用这些内容，必须标为补充来源。
